   403→// Prompt 20 — PLATFORM BILLING FOUNDATION (subscription + entitlement domain).
   404→//
   405→// SEPARATION LAW (docs/billing/platform-billing-vs-business-finance.md):
   406→// these tables model the SaaS subscription of a business TO THIS PLATFORM.
   407→// They must never be mixed with tenant business finance (Sale/Expense/
   408→// Payment), which records the business's OWN customers' money.
   409→//
   410→// Modeling notes:
   411→// - SQLite has no enums → status/type/period/billingPeriod are strings;
   412→//   the authoritative value sets + transition rules live in
   413→//   src/lib/billing/state-machine.ts and are validated at every boundary.
   414→// - Subscription belongs to the BUSINESS (tenant), never to a User (§3).
   415→// - One current subscription per business: unique(businessId) at the DB
   416→//   level (§79). History is preserved via SubscriptionEvent rows; ended
   417→//   subscriptions are never deleted (§81).
   418→// - Plan.code / EntitlementDefinition.code are STABLE machine identifiers
   419→//   (§7/§8) — display names are never used for authorization.
   420→// - No pricing columns anywhere (§39/§40): plan identity is not money.
   421→//   A future payment layer adds its own price/provider tables.
   422→// - No provider-specific ids or secrets (§84/§85) — added by a later
   423→//   payment phase through a dedicated mapping model if justified.
   424→// ---------------------------------------------------------------------------

   537→// ---------------------------------------------------------------------------
   538→// Prompt 21 — USAGE METERING (consumption metrics, NOT resource limits).
   539→//
   540→// Separation of concepts (§4):
   541→// - RESOURCE limits (CUSTOMERS_MAX…) are DERIVED from authoritative tables
   542→//   at check time (Prompt 20) — never duplicated here (§5/§33).
   543→// - CONSUMPTION metrics (AI_REQUESTS / AI_MESSAGES / AI_TOKENS) accumulate
   544→//   over a defined USAGE PERIOD aligned with the subscription billing
   545→//   period (§7) — no cron-based resets (§10/§43): a new billing period
   546→//   simply resolves to a new UsagePeriod row on the next metered operation
   547→//   (lazy, race-safe §76), and historical periods are retained (§101).
   548→//
   549→// Modeling notes:
   550→// - Period identity is deterministic: (businessId, start) is UNIQUE (§8).
   551→//   `end` mirrors the subscription's currentPeriodEnd (null-safe).
   552→// - One counter per (period, metric) (§25/§72); `used` is an INTEGER that
   553→//   only moves through guarded atomic updates (never floats §29/§30).

   562→//   phase can interpret these quantities without altering their meaning

   635→//
   636→// Separation of concerns:
   637→// - The PROVIDER INTERFACE lives in src/lib/payments (registry + adapters).
   638→//   Providers are code+env driven (no provider table): the sandbox "mock"
   639→//   provider is always available for development/testing; real providers
   640→//   only activate when their env keys exist. Unknown → fail closed.
   641→// - PRICES are server-authoritative (src/lib/payments/pricing.ts, EUR minor
   642→//   units) — the browser never supplies an amount; the session snapshots
   643→//   the charged amount at creation time.
   644→// - FULFILLMENT is the ONLY path that changes a plan through a payment:
   645→//   a signature-verified webhook marks the session SUCCEEDED and invokes
   646→//   the idempotent Prompt-20 changePlan(service) — never the reverse, and
   647→//   never any client-asserted "paid" state.
   648→//
   649→// Lifecycle:  PENDING → SUCCEEDED | FAILED | EXPIRED | CANCELED            (terminal)
   650→//                      ↘ RECONCILIATION_REQUIRED                            (terminal,
   651→//   Prompt 23: amount/currency/reference discrepancies from a REAL provider
   652→//   verification are NEVER auto-resolved and NEVER silently "failed" — the
   653→//   discrepancy is recorded (reconciliationReason + metaJson) and the case
   654→//   waits for operator review. See docs/billing/payment-reconciliation.md.
   655→// ---------------------------------------------------------------------------

   669→  // unique per provider.

   671→

   753→// Prompt 24 — currency-aware pricing (price books + versioned plan prices).
   754→//
   755→// A PriceBook is a complete, versioned pricing catalog for ONE settlement
   756→// currency; PlanPrice rows are its immutable per-plan/per-period amounts.
   757→// Rules baked into this schema (docs/billing/pricing-architecture.md):
   758→// - Price changes create a NEW PriceBook version row — PlanPrice amounts are
   759→//   never mutated after creation (§8/§36: no retroactive repricing).
   760→// - A book that any CheckoutSession references can NEVER be deleted
   761→//   (CheckoutSession.priceBookId is onDelete: Restrict) — history is kept.
   762→// - Resolution picks the newest ACTIVE, currently-effective book per
   763→//   currency (effectiveFrom/effectiveTo, server time only — §9/§33).
   764→// - Amounts are INTEGER minor units in the book's currency exponent
   765→//   (EUR=2 cents, IRR=0 rials) — never floats (§22/§23).

   774→  version       String

   776→  // layer (src/lib/payments/currency.ts) at seed and resolution time.
   777→  currency      String
   778→  // Only active books participate in resolution (§10 step 4).
   779→  active        Boolean  @default(false)
   780→  effectiveFrom DateTime @default(now())
   781→  // Books expire automatically after effectiveTo (§9/§33).
   782→  effectiveTo   DateTime?
   783→  description   String   @default("")
   784→
   785→  createdAt        DateTime          @default(now())
   786→  updatedAt        DateTime          @updatedAt
   787→  prices           PlanPrice[]
   788→  checkoutSessions CheckoutSession[]
   789→
   790→  @@unique([code, version])
   791→  @@index([currency, active])
