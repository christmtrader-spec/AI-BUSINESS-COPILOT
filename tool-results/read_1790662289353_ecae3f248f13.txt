   398→// Prompt 20 — PLATFORM BILLING FOUNDATION (subscription + entitlement domain).
   399→//
   400→// SEPARATION LAW (docs/billing/platform-billing-vs-business-finance.md):
   401→// these tables model the SaaS subscription of a business TO THIS PLATFORM.
   402→// They must never be mixed with tenant business finance (Sale/Expense/
   403→// Payment), which records the business's OWN customers' money.
   404→//
   405→// Modeling notes:
   406→// - SQLite has no enums → status/type/period/billingPeriod are strings;
   407→//   the authoritative value sets + transition rules live in
   408→//   src/lib/billing/state-machine.ts and are validated at every boundary.
   409→// - Subscription belongs to the BUSINESS (tenant), never to a User (§3).
   410→// - One current subscription per business: unique(businessId) at the DB
   411→//   level (§79). History is preserved via SubscriptionEvent rows; ended
   412→//   subscriptions are never deleted (§81).
   413→// - Plan.code / EntitlementDefinition.code are STABLE machine identifiers
   414→//   (§7/§8) — display names are never used for authorization.
   415→// - No pricing columns anywhere (§39/§40): plan identity is not money.
   416→//   A future payment layer adds its own price/provider tables.
   417→// - No provider-specific ids or secrets (§84/§85) — added by a later
   418→//   payment phase through a dedicated mapping model if justified.
   419→// ---------------------------------------------------------------------------

   532→// ---------------------------------------------------------------------------
   533→// Prompt 21 — USAGE METERING (consumption metrics, NOT resource limits).
   534→//
   535→// Separation of concepts (§4):
   536→// - RESOURCE limits (CUSTOMERS_MAX…) are DERIVED from authoritative tables
   537→//   at check time (Prompt 20) — never duplicated here (§5/§33).
   538→// - CONSUMPTION metrics (AI_REQUESTS / AI_MESSAGES / AI_TOKENS) accumulate
   539→//   over a defined USAGE PERIOD aligned with the subscription billing
   540→//   period (§7) — no cron-based resets (§10/§43): a new billing period
   541→//   simply resolves to a new UsagePeriod row on the next metered operation
   542→//   (lazy, race-safe §76), and historical periods are retained (§101).
   543→//
   544→// Modeling notes:
   545→// - Period identity is deterministic: (businessId, start) is UNIQUE (§8).
   546→//   `end` mirrors the subscription's currentPeriodEnd (null-safe).
   547→// - One counter per (period, metric) (§25/§72); `used` is an INTEGER that
   548→//   only moves through guarded atomic updates (never floats §29/§30).
   549→// - UsageEvent rows exist ONLY for meaningful consumption (AI usage — §26);
   550→//   idempotencyKey uniqueness ([businessId, metric, idempotencyKey]) makes
   551→//   a network retry NEVER double-charge (§17/§18). Status: COMMITTED
   552→//   (counts) | RELEASED (provider failed before acceptance — reconciled).
