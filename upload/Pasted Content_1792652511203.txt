# PROMPT 63

## AI BUSINESS COPILOT

### Deep Technical Audit, Security Hardening, Defect Remediation, Regression Testing & End-to-End Verification

You are acting as a principal software architect, senior full-stack engineer, application security specialist, database engineer, QA automation engineer, DevOps engineer, and technical auditor.

Your task is to perform a rigorous, evidence-based audit of the EXISTING AI BUSINESS COPILOT codebase, identify and fix verified defects, validate critical security boundaries, execute the available test suites, and produce an accurate final verification report.

This is a controlled remediation phase, not a greenfield development project.

Do not optimize for pleasing the project owner. Optimize for correctness, security, reliability, maintainability, financial integrity, and actual production readiness.

Work directly on the existing repository.

Do not merely provide recommendations. Inspect the implementation, reproduce defects when possible, fix confirmed problems, add regression tests, and verify the changes.

# SECTION 0 — NON-NEGOTIABLE EXECUTION RULES

## 0.1 Inspect Before Modifying

Before changing any file:

1. Identify the actual repository root.
2. Inspect the current Git branch and commit.
3. Inspect the working tree and preserve any existing uncommitted changes.
4. Read the project instructions, including applicable `AGENTS.md`, README files, package scripts, configuration files, and relevant Worklog entries.
5. Inspect the latest project architecture and dependency configuration.
6. Identify the actual implementations of the platform-admin, authentication, RBAC, support, billing, pricing, AI-cost, audit, tenant-isolation, and notification subsystems.
7. Determine which parts of Prompt 62 already exist.
8. Identify existing tests and their actual execution commands.
9. Establish a baseline before making changes.

Do not assume that the repository still matches an earlier inspection. The current repository is the source of truth.

If the current codebase differs from previous reports, follow the current implementation and document the discrepancy.

## 0.2 Preserve Existing Functionality

Follow strict incremental-development principles.

* Do not rewrite working modules merely to simplify the audit.
* Do not replace the application architecture.
* Do not migrate frameworks.
* Do not introduce PostgreSQL, Redis, or other infrastructure without a demonstrated technical necessity and explicit project justification.
* Do not delete existing functionality to make tests pass.
* Do not silently weaken authentication, authorization, validation, financial controls, or tenant isolation.
* Do not change public API contracts unnecessarily.
* Do not introduce unrelated features.
* Do not overwrite user changes.
* Do not create duplicate services or competing sources of truth.
* Do not create another platform-admin panel.
* Do not mark unfinished functionality as implemented.
* Do not disable failing tests simply to obtain a green result.

Every modification must have a clear technical justification.

Prefer the smallest safe fix that addresses the verified root cause.

## 0.3 Evidence-Based Reporting

For every important finding, record:

* Finding ID.
* Severity.
* Affected module or file.
* Exact defect or risk.
* Evidence supporting the finding.
* Whether the issue was reproduced.
* Root cause.
* Applied fix, if any.
* Regression test added or updated.
* Actual verification result.
* Remaining limitations.

Use these statuses consistently:

* `EXECUTED-PASS`
* `EXECUTED-FAIL`
* `BLOCKED`
* `NOT-EXECUTED`
* `REPORTED-FROM-WORKLOG`
* `STATIC-REVIEW-ONLY`

Never report a test as executed unless the command or test actually ran and its result was observed.

A previous Worklog entry is historical evidence, not proof that the current code passes.

If a command fails because of missing dependencies, credentials, unavailable services, environment restrictions, or unrelated infrastructure, report the exact blocker. Do not convert a blocked test into a pass.

Never invent test counts, browser results, coverage percentages, security certifications, or production-readiness claims.

## 2.1 Authentication

Verify that:

* Platform-admin requests require authenticated platform-operator sessions.
* Tenant membership or tenant-admin privileges do not grant platform-admin access.
* Platform privileges are derived from trusted server-side data.
* Session invalidation and session-version checks are consistently enforced.
* Disabled, suspended, expired, or otherwise invalid sessions cannot perform protected operations.
* High-risk actions require the documented reauthentication process.
* Authentication errors do not disclose sensitive internal information.
* No endpoint trusts a client-supplied role, permission list, or operator identity.
* Bootstrap procedures do not expose default credentials or public privilege-escalation endpoints.

Test both successful and unsuccessful authentication paths.

## 2.2 Authorization and Permission Boundaries

Audit every platform API route and its HTTP methods.

Build an inventory containing:

* Route and HTTP method.
* Authentication requirement.
* Required permission.
* Additional validation.
* Reauthentication requirement, where applicable.
* Audit-log behavior.
* Test coverage.
* Verification status.

Verify that authorization is enforced on the server for every protected operation.

UI visibility is not authorization.

Test the existing roles individually, including:

* `PLATFORM_SUPER_ADMIN`
* `PLATFORM_SUPPORT`
* `PLATFORM_BILLING`
* `PLATFORM_AI_COST`
* `PLATFORM_SECURITY`
* `PLATFORM_READONLY`

Use the roles actually defined by the current codebase if they have changed.

Verify that permissions follow least privilege.

A read-only operator must not be able to perform mutations by calling an API directly.

A support operator must not gain billing, security, or unrestricted user-management privileges unless explicitly granted by the documented permission model.

Test both allowed and forbidden operations.

Check for:

* Missing permission checks.
* Incorrect permission mappings.
* Inconsistent checks between routes.
* Insecure default behavior.
* Object-level authorization failures.
* Privilege escalation.
* HTTP method bypasses.
* Unprotected secondary endpoints.
* Inconsistent error responses that reveal protected information.

Do not assume every route file corresponds to exactly one endpoint. Count route files, exported HTTP handlers, and actual logical endpoints separately when reporting coverage.

## 2.3 Super-Admin Lifecycle

Verify that:

* The last active super-admin cannot be removed or disabled through ordinary lifecycle operations.
* Concurrent operations cannot trivially bypass the last-super-admin safeguard.
* Platform operators cannot accidentally suspend or modify their own account in a way that locks the platform out, unless an explicitly safe recovery mechanism exists.
* Operator bootstrap and recovery procedures are documented and appropriately restricted.
* Role changes, deactivation, and other privileged lifecycle operations are audited.

# SECTION 12 — ROOT-CAUSE REMEDIATION

After baseline inspection, prioritize findings according to risk.

Suggested priority:

* P0: Critical data exposure, privilege escalation, financial corruption, or account takeover.
* P1: High-impact authorization, payment, tenant-isolation, or quota-enforcement defects.
* P2: Significant correctness, reliability, workflow, or operational defects.
* P3: Minor defects, usability issues, and maintainability improvements.

For each confirmed defect:

1. Reproduce the issue when feasible.
2. Identify the root cause.
3. Implement the smallest safe fix.
4. Add or update a regression test.
5. Run the relevant targeted test.
6. Run broader regression tests affected by the change.
7. Review the diff for unintended side effects.
8. Record the outcome in the findings register.

If the defect cannot be reproduced but a credible code-level vulnerability is visible, document the evidence and confidence level.

Do not silently skip difficult findings.

If a fix would require a significant architectural change, data migration, unavailable credentials, or a risky production operation, document the blocker and propose a safe implementation plan rather than making an unreviewed high-risk change.

Do not claim that the entire project is bug-free. The goal is to identify and remediate the defects discoverable within the defined scope and environment.
