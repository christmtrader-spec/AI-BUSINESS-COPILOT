* Client-controlled role or identity fields.
* Horizontal privilege escalation.

Create a route-by-route authorization matrix based on the actual codebase.

Do not merely sample a few routes and claim that the entire platform has been audited.

## 3.2 RBAC integrity

Inspect the existing six platform roles:

* `PLATFORM_SUPER_ADMIN`
* `PLATFORM_SUPPORT`
* `PLATFORM_BILLING`
* `PLATFORM_AI_COST`
* `PLATFORM_SECURITY`
* `PLATFORM_READONLY`

Verify the actual role names and permission definitions in the repository before changing anything.

Test whether:

* Each role receives only its intended permissions.
* Read-only operators cannot perform mutations.
* Support operators cannot access unrelated billing or security operations.
* Billing operators cannot grant themselves additional privileges.
* AI-cost operators cannot modify pricing unless explicitly authorized.
* Security operators cannot silently change their own role.
* Operators cannot assign permissions outside their authority.
* Role changes are authorized by the correct permission.
* Unknown roles and unknown permissions are denied.
* Missing permissions result in denial.
* Authorization failures do not accidentally fall back to a privileged role.
* Frontend access-matrix information matches the actual server-side permission registry.

Keep one authoritative permission registry.

If permission definitions are duplicated, consolidate them only when necessary and without breaking existing contracts.

## 3.3 Authentication session and MFA security

Inspect the existing NextAuth-based authentication flow and platform MFA implementation.

Verify:

* Platform administrators cannot bypass required MFA through direct API calls.
* Direct navigation cannot bypass the MFA gate.
* Expired or invalid sessions are rejected.
* Session revocation takes effect on subsequent protected requests.
* Logout-current-device actually revokes or invalidates the relevant session according to the existing session architecture.
* Logout-all-devices cannot be invoked by an unauthorized operator.
* Session-management endpoints do not expose session secrets.
* TOTP verification resists replay.
* Recovery codes are single-use and stored safely.
* MFA enrollment cannot be completed by an unauthorized actor.
* MFA disabling or recovery procedures require appropriate reauthentication and authorization.
* MFA configuration failures do not silently disable enforcement.
* Security-sensitive actions cannot rely solely on a stale client-side authentication state.
* Session and device information is disclosed only to appropriately authorized users.

Preserve existing authentication behavior for ordinary tenants.

Do not impose platform-administrator MFA requirements on tenant users unless the existing product specification explicitly requires it.

## 3.4 Operator invitations and onboarding

Inspect the complete invitation lifecycle:

* Invitation creation.
* Token generation.
* Token storage.
* Token presentation.
* Invitation redemption.
* Invitation expiration.
* Invitation revocation, if supported.
* Duplicate redemption.
* Concurrent redemption.
* Operator creation.
* Audit logging.
* Error handling.

Verify that:

* Invitation tokens are generated using cryptographically secure randomness.
* Raw invitation tokens are not stored unnecessarily.
* Tokens are not written to ordinary application logs.
* Tokens are not included in list responses or unrelated DTOs.
* Expired invitations cannot be redeemed.
* Revoked or already redeemed invitations cannot be reused.
* Concurrent requests cannot redeem one invitation more than once.
* The recipient cannot choose an arbitrary privileged role.
* Only appropriately authorized operators can create invitations.
* Invitation acceptance does not bypass the normal authentication and MFA requirements.
* Error responses do not reveal unnecessary internal information.

The existing invitation flow uses out-of-band link delivery.

Do not introduce a new email provider or fabricate delivery functionality.

If email delivery is not configured, document that limitation and retain a secure out-of-band workflow.

## 3.5 First-operator setup key

Audit the existing offline setup-key mechanism.

Verify:

* Setup keys are generated using cryptographically secure randomness.
* Only a hash or equivalent non-reversible verifier is persisted.
* The raw key is never exposed through ordinary API responses or logs.
* Expiration is enforced server-side.
* Invalid, expired, revoked, and already-used keys are rejected.
* Key redemption is atomic under concurrent requests.
* The setup flow cannot create multiple initial operators.
* The setup flow becomes unavailable after the initial operator has been established.
* A race condition cannot reopen bootstrap access.
* Unauthorized users cannot inspect setup-key hashes or status secrets.
* Database errors fail safely.
* Setup-key creation remains an offline administrative operation.
* The ordinary login flow does not become an alternate bootstrap path.
* Existing installations with one or more operators cannot accidentally re-enter initial setup.

Verify the setup TTL rules and input validation against the existing implementation.

Do not generate a new live production setup key during tests.

Do not print real setup secrets in logs, test reports, screenshots, or the final response.

## 3.6 Approval framework

Inspect the existing platform approval state machine, payload binding, and execution path.

Verify:

* Only valid state transitions are accepted.
* An operator cannot approve their own request.
* Approval identity is derived from authenticated server-side operator identity.
* Client-provided operator IDs are not trusted.
* Expired requests cannot execute.
* Rejected or cancelled requests cannot execute.
* Repeated requests cannot execute the same operation twice.
* Concurrent approvals cannot cause duplicate execution.
* The canonical payload hash binds the approval to the exact requested action and parameters.
* Payload changes invalidate the original approval.
* The target action is revalidated immediately before execution.
* Reauthentication requirements are enforced server-side.
* Failed execution is recorded accurately.
* Approval decisions and execution outcomes are audited.
* The requester cannot alter an approval after it has been approved.
* Transaction boundaries and uniqueness constraints provide real concurrency safety.

Review the existing 24-hour approval TTL and state machine rather than assuming those settings are correct.

Preserve existing atomic execution guarantees.

6. Do not accept a client-provided amount as the authoritative financial truth.
7. Revalidate the underlying records before execution.
8. Prevent duplicate reconciliation.
9. Use appropriate database transaction boundaries.
10. Reject requester self-approval.
11. Enforce the required server-side permissions.
12. Audit the request, decision, execution, and outcome.

## 3.7 Audit logs and security-event handling

Inspect the existing audit and security-event system.

Verify:

* Sensitive administrative actions create appropriate audit records.
* Audit actor identity comes from the authenticated server context.
* Audit records contain sufficient action, target, timestamp, and outcome information.
* Passwords, session secrets, TOTP secrets, recovery codes, setup keys, and raw invitation tokens are never logged.

Do not claim that the audit log is cryptographically immutable unless the implementation actually provides that property.
