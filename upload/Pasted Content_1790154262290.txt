============================================================
1. PRIMARY OBJECTIVE
============================================================

Implement a robust server-side usage metering system.

The system must be able to answer:

- How much has this business consumed?
- During which usage period?
- Which limits apply?
- How much remains?
- Has a quota been reached?
- Can the requested operation proceed?
- Can an operation be retried without double-counting?
- Can a malicious client bypass the limit?
- Can concurrent requests exceed the limit?

The usage system must be designed primarily for SaaS consumption controls.

3. CORE PRINCIPLE
============================================================

The client is NEVER the source of truth for usage.

Never trust:

localStorage
sessionStorage
cookies controlled by client
client Zustand state
query parameters

frontend plan data

as authoritative usage.

The authoritative usage must be determined by server-side logic and database state.

============================================================
7. USAGE PERIOD MODEL
============================================================

Usage must belong to a defined period.

Prefer alignment with the Business subscription billing period.

Example:

Subscription:
currentPeriodStart
currentPeriodEnd

Usage:
periodStart
periodEnd

This prevents usage resets from depending on:

server restart
cron job
local timezone
manual reset

DO NOT build a "reset usage every first day of month" mechanism if the subscription billing period is different.

============================================================
8. PERIOD IDENTITY
============================================================

Every usage period must have a stable identity.

Conceptually:

usagePeriodId

or a deterministic compound identity such as:

businessId + periodStart + periodEnd

There must be no ambiguity about which usage period a record belongs to.

============================================================
9. USAGE PERIOD CREATION
============================================================

When a metered operation occurs:

1. Resolve business.
2. Resolve active subscription.
3. Resolve current entitlement.
4. Determine current billing/usage period.
5. Find or create UsagePeriod.
6. Verify quota.
7. Meter operation atomically.
8. Proceed with operation.

The implementation must be safe under concurrency.

"reset monthly usage via cron"

unless required for a separate cleanup process.

16. AI REQUEST ID
============================================================

Every metered AI execution should have a unique request/correlation identifier.

Use a cryptographically safe or UUID-style identifier.

============================================================
17. IDEMPOTENCY
============================================================

This is CRITICAL.

A network retry must NOT double-charge usage.

Example:

Request A
→ AI operation starts
→ usage recorded
→ response lost
→ client retries

The retry must not create another identical usage event simply because the client retried.

Use an idempotency key or server-generated operation ID.

The exact design must fit the existing AI architecture.

============================================================
18. IDEMPOTENCY KEY STORAGE
============================================================

If usage events are persisted:

store enough information to detect duplicate operations.

Possible fields:

idempotencyKey
businessId
metric
periodId
createdAt

with a uniqueness constraint appropriate to the operation semantics.

Do not create an overly broad unique constraint that blocks legitimate operations.

============================================================
19. CONCURRENCY
============================================================

The system must prevent quota bypass under concurrent requests.

Example:

AI quota:
100 requests

Current usage:
99

Two requests arrive simultaneously.

Expected:

Only one should consume the final available slot.

The second must be rejected.

Do not implement:

read count
→ application check
→ increment

as separate unsafe operations if that creates a race condition.

Use an atomic or transactional mechanism.

============================================================
20. RESERVATION VS COMMIT
============================================================

Consider whether the AI operation should:

A. Count before provider call
B. Count after successful provider call
C. Reserve before and reconcile after

Choose one strategy based on existing AI behavior.

For quota protection, a reservation-before-provider-call approach may be appropriate.

But do not permanently consume usage when a request fails for infrastructure reasons unless the documented policy intentionally does so.

Document:

- failed AI call behavior
- provider timeout behavior
- user cancellation
- server exception
- retry behavior

22. QUOTA TYPES
============================================================

Support at least:

HARD_LIMIT

and conceptually allow:

Operation blocked when quota is exceeded.

SOFT_LIMIT:

Do NOT activate soft-limit behavior unless the current product policy requires it.
